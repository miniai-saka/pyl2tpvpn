# 通信の仕組みと実装上の上限

## Python内の通信をVPNへ流す仕組み

外側の通信には、接続先のIKE・NAT-Tポートへ接続したIPv4 UDPソケットを使います。
VPNサーバー自身のホスト名は接続前にOSで名前解決しますが、VPN内でアクセスする相手の名前解決は、VPN内のDNSを使います。

`VPNClient` がIKE、ESP、必要に応じたL2TP・PPPと、IPv4の通信処理をまとめて管理します。
OSのルーティングテーブル・インターフェース・DNS・ファイアウォールや、Python全体のソケット・Requests設定は変更しません。

TCP・UDP・ICMP・DNSはこのIPスタック上で動き、TLSにはPythonの `ssl.MemoryBIO` を使います。
非同期APIを使う場合はイベントループを継続して動かし、同期処理では `VPNRuntime` の別スレッドを使います。

## 鍵更新と死活監視

IKEの再送では、同じ暗号化済み要求を、待ち時間を延ばしながら送ります。死活監視と鍵更新は別タスクで動かし、応答待ちによって更新の開始まで止まることを避けています。

IKEv2で自分から行う要求は、一度に一つへ直列化します。相手からの要求は別のカウンターと応答キャッシュで処理します。
同時リキーではnonceで選択を合わせ、異なる操作が競合した場合はTEMPORARY_FAILUREで時間を空けて再試行します。

既定のIKE寿命は28,800秒、CHILD SA寿命は3,600秒で、寿命の20%手前から更新します。ESPは使用量やシーケンス番号でも更新を開始します。
上限を超えた鍵は使用せず、時刻の管理には単調増加の時計を使います。
旧受信ESP SAは独立したリプレイ状態を持ち、重複期間中の受信を許可しますが、ハード寿命を超えて保持・使用しません。

`rekeys.child` は初回を含むSAインストール回数です。`rekeys.ike` と `rekeys.reauth` は初回接続後の更新を数えます。

## 入力とメモリーの上限

ネイティブIKEv2では、割り当てアドレスと交渉済みセレクターを通信時に確認します。ポートの確認は、送信時は断片化の前、受信時は再構成の後に行います。

| 対象 | 上限・扱い |
| --- | --- |
| IPv4断片の再構成 | 64件、合計1 MiB、15秒で失効。重複する断片を拒否 |
| DNSキャッシュ | 最大1,024件 |
| 重複期間中の受信ESP SA | 最大64個 |
| PPP・制御キュー・TCPバッファー | それぞれ上限付き |

TCPはACK、送受信ウィンドウ、輻輳制御、並べ替え、再送、ゼロウィンドウの確認、FIN/RST、シーケンス番号の周回、能動切断時のTIME_WAITを処理します。
SACK・TCP timestamps・window scalingは通知しません。OSの全ソケット機能を置き換えるための実装ではありません。

## 切断処理

鍵更新などのタスクを止め、アプリケーション側の通信を閉じてから、PPP・L2TP・IKEを順に終了します。
PPPのTerminate-Ack、L2TPのStopCCN ACK、IKEv2の削除応答を時間制限付きで待ち、UDP送信が完了した後にソケットを閉じます。同時に `close()` が呼ばれても後処理を共有します。

プロセスの強制終了や回線切断では、相手側の状態が自動終了まで残る場合があります。接続先の死活監視と終了方針も必要です。
接続先に合わせて選ぶ設定は[互換性について](INTEROPERABILITY.md)にまとめています。
